# GPS 方法可行性记录

评估日期：2026-10-15。结论：**距离反推方法在给定协议和距离模型下有条件可行；当前浙大服务端兼容性尚未实测确认。** 用户目前没有可测试的进行中 GPS 活动，本轮没有使用账号提交真实签到。

## 公开依据与限制

[XMU-AC 主程序](https://github.com/spicysuimai/XMU-AC/blob/master/auto_checkin.py) 向 GPS 签到接口提交两个参考位置，依据服务端返回距离计算圆交点，再尝试候选位置。它使用厦门固定参考点和局部平面近似；两个距离通常对应两个候选点，且探测本身就是签到写请求。

[浙大公开调用实例](https://github.com/5dbwat4/ZJU-live-better/blob/main/courses.zju/autosign.js) 使用 `PUT /api/rollcall/{id}/answer?api_version=1.1.2`，携带经纬度及设备标识，并从响应中收集距离进行球面拟合。它为浙大曾有同类调用提供依据，但历史源码及作者成功描述不能证明现行平台继续开放相同能力。文中的历史范围值不作为本项目判定标准。

| 条件 | 本轮证据 | 尚需确认 |
| --- | --- | --- |
| GPS 提交接口与基本字段 | 厦大及浙大公开调用代码 | 现行浙大活动是否接受同一请求 |
| 范围外响应包含距离 | 公开脚本依赖此字段 | 当前账号能否获得有效数值距离 |
| 距离为探测点到同一签到中心的米制距离 | 可在模拟数据中检验算法 | 真实距离的单位、含义、精度及坐标系 |
| 设备、权限、风控允许提交 | 公共代码不足以保证 | 真实活动的服务端限制 |
| 本人状态确认成功 | 沿用本项目本人记录查询路径 | 真实 GPS 成功后记录及可见延迟 |

## 本项目的计算验证

未复制厦大源码，也未沿用厦门参考点。独立实现分为距离拟合与终端提交两层：

1. 使用杭州附近三个不共线的人工参考位置，消除仅凭两个距离选择候选点的歧义。
2. 用平方距离方程得到初始估计，再以大圆距离做最多 25 步最小二乘迭代。平面坐标只用于初值和迭代参数，最终误差在球面上计算。
3. 分别尝试平均地球半径 `6371000` 米与浙大公开实现采用的 `6372999.26` 米，选取最大残差较小的拟合。两者都是模型候选，并非本轮测得的服务端参数。
4. 三份距离的最大残差不得超过 10 米；不一致就停止。这是模型一致性门槛，不是平台允许的签到半径，也不能证明真实定位精度。

离线测试以独立的三维单位向量和 `atan2` 距离算法生成基准，而非使用生产代码反向生成同一公式的测试数据。模拟点覆盖杭州附近、海宁方向、舟山方向及前两探测点连线附近；分别测试两种地球半径和整数米距离取整，要求估计位置与模拟真值误差小于 5 米。公里单位误当米、距离扣除范围半径及互不一致的第三份距离等样例必须被拒绝。

这些结果验证计算在上述样例和假设下成立，不能替代真实平台测试。模型外的距离算法、噪声、位置移动或其他响应语义可能导致失败；一致性检查也不是对全部错误语义的证明。

## 运行约束

所有位置请求均在终端明确确认之后发送，包括探测。确认提示说明会推算签到点、不读取本机真实位置、最多四个定位写请求，探测也可能直接签到。每次请求前重新检查活动及本人状态；只对明确的 `radar_out_of_scope` 响应和有效距离继续下一位置。

HTTP 200、超时、限流、服务端错误、无法解析的提交响应均不授权继续下一位置；程序只回查本人记录。只有 `on_call` / `on_call_fine` 才显示成功。权限、设备或其他业务拒绝直接停止，不用随错误附带的距离继续推算。最终位置仍范围外时停止，不追加探测或循环重试。程序重启后需重新人工确认。

日志不保存坐标、实际距离、Cookie、密码、原始响应或名单。现有直连会话和 TLS 证书校验同样用于 GPS 请求，无需浏览器；没有新增第三方依赖。

## 有活动时的验证方式

运行 `python -m zju_ac`，检测到本人活动后，在终端确认一次。预期可能是探测直接成功，也可能是三份距离检查通过后提交计算位置。以程序回查和正常客户端中的本人记录共同确认结果。

若提示距离缺失、设备拒绝或模型不兼容，记录终端安全错误文本即可，程序不会自动重试该活动。若需要进一步检查协议，只提供字段名、HTTP 状态及错误类别，移除账号、票据、Cookie、数字码、实际坐标、距离和个人信息。仍在等待此步骤完成后，才能将该功能视为对真实活动验证通过。
